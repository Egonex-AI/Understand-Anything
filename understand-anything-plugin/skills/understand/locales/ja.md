# 日本語出力ガイドライン (Japanese)

本ファイルは、日本語でナレッジグラフコンテンツを生成する際の言語固有のガイドラインを提供します。

## 適用範囲

自然言語で書くすべての説明を日本語にする。対象は、プロジェクト概要、ファイル・関数・クラスの責務、データフローと依存関係の説明、レイヤーの役割、ツアーのタイトル・説明・判断理由、`languageNotes`、`languageLesson`、エッジの`description`、およびフォールバック文言である。READMEやコメントが英語でも、意味を理解して日本語で説明する。

ファイル名、関数名、変数名、型名、API名、フレームワーク名、ライブラリ名、パス、node ID、edge type、JSONキーは原文のまま保持する。コードやJSONの構造を翻訳せず、識別子の周囲に自然な日本語の説明を加える。標準訳がない技術用語は英語のまま使用してよいが、文全体を英語に戻してはならない。

説明が生成できない場合は`No description available`などの英語プレースホルダーを使わず、「説明はありません。」のように日本語で書く。100ファイル超過などの注意書きも日本語にする。

## タグの命名規則

日本語タグまたは英語の一般的な技術用語を使用：

| パターン | 推奨タグ |
|---------|---------|
| エントリーポイント | `入口点`, `barrel`, `exports` または `entry-point` |
| ユーティリティ | `ユーティリティ`, `helpers`, `utility` |
| APIハンドラー | `api-handler`, `controller`, `endpoint` |
| データモデル | `データモデル`, `entity`, `schema` または `data-model` |
| テストファイル | `テスト`, `unit-test`, `test` |
| 設定ファイル | `設定`, `build-system`, `configuration` |
| インフラ | `インフラ`, `deployment`, `infrastructure` |
| ドキュメント | `ドキュメント`, `guide`, `documentation` |

**混合戦略：** 一般的な技術用語は英語を保持（`middleware`, `api-handler`など）、説明用タグは日本語を使用可能。

タグは意味を表す語を日本語にしてよい。`middleware`、`hook`、`barrel`、`entry-point`、`REST API`など、コード検索や技術上の識別に役立つ語は英語のまま残してよい。タグを日本語にする場合も、ファイル名や関数名をタグへ置き換えない。

## サマリーのスタイル

1-2文のサマリーを日本語で記述：
- ファイルの**目的**と**役割**を説明
- 能動態を使用（「提供する...」「処理する...」「管理する...」）
- ファイル名の繰り返しを避ける

**例：**
- 良い: "API層全体で使用される日付フォーマットと文字列サニタイズのヘルパー関数を提供。"
- 悪い: "utilsファイルにはユーティリティ関数が含まれています。"

責務・関係・判断理由を含める例：
- 責務: "空き時間の入力を検証し、Supabaseへの保存に必要なデータへ変換する。"
- データフロー: "`EventForm`の入力を検証して`events`へ渡し、保存結果をカレンダー表示へ反映する。"
- 依存関係の理由: "このroute handlerは認証済みユーザーを確認してからサービス層を呼び出すため、画面からデータ層への直接アクセスを避けられる。"

## 技術用語

以下の用語は英語を保持（標準翻訳がない場合）：
- `middleware`, `hook`, `barrel`, `entry-point`
- `ORM`, `REST API`, `CI/CD`, `CRUD`
- `singleton`, `factory`, `observer`
- `interceptor`, `guard`

## レイヤー名

日本語のレイヤー名を使用：
- `API層`, `サービス層`, `データ層`, `UI層`
- `インフラ`, `設定`, `ドキュメント`
- `ユーティリティ層`, `ミドルウェア層`, `テスト層`

または英語を保持（チームの慣習に従う）：
- `API Layer`, `Service Layer`, `Data Layer`
